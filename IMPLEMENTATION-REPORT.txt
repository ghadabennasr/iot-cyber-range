CYBERRANGE SECURITY-LAB IMPLEMENTATION REPORT
Prepared: 2026-10-13

PURPOSE
=======

This report documents the security-lab work carried out in the CyberRange
workspace in response to the request to finish the Infrastructure &
Cybersecurity Lead tasks. It records the goal, design approach, additions,
modifications, intentional removals/replacements, validation, and work still
outside this scope.

This report deliberately does not reproduce passwords, password hashes,
tokens, or other local secrets. Broker credentials and runtime event data
belong in ignored local files, not in this report or source control.


EXECUTIVE SUMMARY
=================

The existing project already had a Mosquitto broker, topic ACLs, password
authentication, a badge-controller project, and a local Bore workflow. The
remaining security-lead work was to provide an isolated and demonstrable
attack/detection/response lab without implementing the teammate-owned backend.

The delivered lab adds:

  * An on-demand attacker container restricted to the Compose lab network.
  * Four bounded exercises: anonymous-access reconnaissance, harmless
    command-like input to a fake maintenance service, an out-of-range
    simulated sensor reading, and an attempted unauthorized lock command.
  * A fake TCP honeypot that records requests and never invokes a shell or
    executes received input.
  * A Python IDS monitor that reads MQTT publications, Mosquitto audit logs,
    and honeypot events; applies simple detection rules; and writes events
    and alerts to local SQLite.
  * A local dashboard/API for viewing events and alerts and requesting an
    operator-controlled broker-account block.
  * A host-side PowerShell response tool that applies queued requests by
    changing a marked section of the ACL and restarting Mosquitto.
  * Project documentation, ignored local-state paths, tests, and a repaired
    first-run broker-user helper.

The teammate-owned application backend, the remaining two ESP32 firmwares,
and full integration with those not-yet-built components remain out of scope
and are not claimed as complete.


GOAL AND DESIGN VISION
======================

The intended demonstration is a contained security lifecycle:

  simulated device / lab exercise
      -> broker and honeypot activity
      -> IDS observation
      -> event storage and alert
      -> human review in the dashboard
      -> optional, explicit local containment action

The goal was not to build a production IDS or expose a real attack surface.
The goal was to give the project a reproducible and safe security exercise
that illustrates the controls already being built around the IoT devices:
authentication, least-privilege MQTT topics, auditability, detection,
investigation, and a deliberate response.

The design choices follow these principles:

  1. Containment first. The attacker, honeypot, and security monitor operate
     on an internal Docker network. Attacker and honeypot ports are not
     published to the host or internet.
  2. Safe simulations. The command-injection payload is only text sent to a
     fake TCP listener. There is no shell invocation, command execution, or
     arbitrary target discovery.
  3. Least privilege. The IDS receives only its own MQTT credential through a
     Compose secret, rather than being given the whole local credential
     backup. Device accounts are limited by the broker ACL.
  4. Human-controlled response. A dashboard request only queues a local
     action. A host operator must run the PowerShell watcher for it to edit
     the broker ACL and restart the broker.
  5. Local visibility, not public exposure. Broker and dashboard ports are
     bound to loopback. A separate network path is used for host-published
     ports because Docker Desktop on this Windows setup did not publish
     ports directly from an internal-only network.
  6. No teammate-owned backend coupling. The local lab dashboard/API is a
     separate security tool; it is not the application backend and does not
     impersonate its unfinished ingestion/API responsibilities.


WORKFLOW / DEMARCHE
===================

1. Reviewed the existing project context and the user's ownership boundary.
   The user identified the backend as teammate-owned, so the work focused on
   attacker exercises, honeypot, detections, dashboard/alerts, response, and
   security testing. The backend was left untouched.

2. Reconciled the existing MQTT identities and topics with the role names
   already used in the project. The effective device topics are badge1,
   motion1, and lock1; the controller writes lock commands. Documentation
   references were corrected where they did not match these actual names.

3. Investigated the local broker environment and file handling. Mosquitto
   runs as its own container user and needs readable password/ACL files. The
   helper and response path therefore set ownership and restrictive mode
   through the Mosquitto image instead of assuming Windows bind-mount
   ownership behaves like native Linux.

4. Added the Compose topology and separated internal service communication
   from the host-access route. The first implementation exposed a Docker
   Desktop behavior: publishing a port for a service attached only to an
   internal network did not work in this environment. The topology was
   adjusted so only Mosquitto and a small dashboard proxy also attach to a
   non-internal host-access network. Their ports still bind to 127.0.0.1.

5. Implemented attack exercises with narrowly scoped behavior, then
   exercised them against the live stack. The recon test initially attempted
   an MQTT subscription and assumed the broker would reject the subscription
   request itself. Testing showed the broker accepted the subscription
   request at that protocol stage; read ACL enforcement occurs when messages
   are delivered. To make the exercise verify the intended
   allow_anonymous=false control reliably, recon was changed to perform an
   anonymous MQTT connection and require the broker to reject it.

6. Added IDS ingestion, detection rules, local persistence, and the dashboard.
   The event pipeline was tested using individual rules and then through
   end-to-end exercises. This included testing that honeypot activity and a
   subsequent broker denial from the same source can be correlated.

7. Added a queue-and-apply response workflow rather than letting a web
   request directly control the host or Docker daemon. The host-side watcher
   validates the username/action, manages only its marked ACL section,
   records a result, fixes the ACL file permissions, and restarts the broker.

8. Rebuilt services and tested the code and runtime. Failures found during
   validation were used to improve the implementation: the password helper's
   first-user mode was corrected; the recon test was changed to measure an
   actual rejected anonymous connection; and a Paho client cleanup call was
   corrected after the installed library did not provide that method.

9. Updated README setup/status guidance to distinguish completed controlled
   lab integration from the still-pending full test with the other devices
   and teammate-owned backend.

Added or configured these services:

  security-monitor
    * Builds from Lab/Dockerfile and runs the IDS/dashboard API process.
    * Depends on the broker and honeypot.
    * Receives the IDS password using a Compose secret.
    * Reads runtime events and read-only broker audit logs.
    * Joins only the internal cyberrange network.

  dashboard-proxy
    * Uses nginx:alpine to make the monitor's dashboard available at
      127.0.0.1:8080.
    * Uses a read-only root filesystem and temporary writable cache/run
      directories.
    * Connects to both the internal network and host-access network.
    * The proxy is used to publish a host port without publishing the IDS
      service itself.

  attacker
    * Builds from Attacker/Dockerfile.
    * Is behind the optional "tools" Compose profile, so it is only run when
      explicitly requested.
    * Receives MQTT credentials through environment variables populated by
      the scenario launcher for authenticated tests.
    * Joins only the internal network.

Added the internal cyberrange and separate host-access networks, broker-log
volume, and ids_password secret sourced from Broker/ids.password. This
topology keeps the security tools isolated while permitting loopback-only
host access to the broker and dashboard.

Broker/add-user.ps1  [modified]
-------------------------------

Changes:

  * Calls mosquitto_passwd explicitly via the eclipse-mosquitto:2 image,
    rather than relying on a host installation.
  * Supports an optional supplied password or generates a random password
    when omitted.
  * Creates the local passwordfile if it is missing.
  * Sets password-file ownership to the Mosquitto user and mode to 600 using
    a short-lived Mosquitto container.
  * Calls mosquitto_passwd in batch mode to add/update the requested user.
  * Checks each Docker/mosquitto_passwd exit status and throws on failure.
    It prints the credential only after the password tool reports success.

Why: earlier attempts displayed Mosquitto's usage help because the helper
did not construct the password-tool invocation correctly, and it could
mislead users into believing a credential was saved. A first-run test then
found that `-c` failed because the helper had already created an empty file;
the implementation was corrected to use the normal add/update mode on that
empty file. It was verified by creating two test users in a temporary
directory and confirming hashed entries and Mosquitto readability.


Broker/mosquitto.conf  [modified]
---------------------------------

Retained the MQTT listener on port 1883 and references to the ACL and
password file, with anonymous access disabled. Added audit logging to both
stdout and `/mosquitto/log/mosquitto.log`, with all log types enabled.

Why: stdout is useful for Docker Compose logs, while the file-backed audit
stream is shared read-only with the IDS so that authorization denials and
connection metadata can become events/alerts.


Broker/acl.conf  [modified]
--------------------------

Added/retained topic permissions matching the project role names:

  * badge1 can write under facility/badge1/#.
  * motion1 can write under facility/motion1/#.
  * lock1 can read facility/lock1/cmd and write facility/lock1/state.
  * controller can write facility/lock1/cmd.
  * backend and ids can read facility/#.

Added begin/end markers for a response-managed block section. The PowerShell
response tool inserts per-user deny rules inside that section, preserving the
base permissions below it. This lets the lab apply and remove local
containment blocks without replacing the permanent ACL definitions.

Attacker/attacker.py  [added, then refined]
------------------------------------------

Provides four selectable exercises:

  recon
    * Connects to the fake honeypot for a simple banner/request interaction.
    * Opens an MQTT connection without credentials.
    * Treats broker acceptance as a test failure; expects the broker to reject
      the connection because anonymous access is disabled.
    * Uses an event/callback and bounded wait, then disconnects cleanly.

  command-injection
    * Sends URL-encoded command-like text to the fake maintenance service.
    * Does not execute the text or run a command on any host.

  sensor-spoof
    * Authenticates as the motion1 test account and publishes a simulated
      motion reading with an invalid distance value.
    * The IDS should raise a sensor-range-anomaly alert.

  lateral-movement
    * Touches the honeypot, then authenticates with the low-privilege badge
      account and attempts to publish to the lock command topic.
    * The broker ACL is expected to deny the unauthorized write.
    * The monitor can correlate honeypot access and a subsequent broker
      denial from the same lab source.

The runner confines destination defaults to Compose service names. MQTT
scenarios require supplied credentials; the PowerShell wrapper extracts the
needed credential from the ignored local credential file and writes a
temporary ignored env file for Compose. That file is removed after the
scenario completes.

Important refinement: an early recon implementation attempted subscriptions
to broad/protected topics and assumed SUBSCRIBE itself would be denied.
Observed Mosquitto behavior showed that was not a reliable test of read
authorization. Recon was changed to test the explicitly configured
anonymous-access prohibition, which produced a verifiable broker rejection
and IDS event.

Lab/honeypot.py  [added]
------------------------

Implements a threaded fake TCP maintenance console:

  * Listens on internal port 2323.
  * Reads at most a bounded request line and applies a socket timeout.
  * Decodes URL-encoded text before checking command-like markers so encoded
    separators such as `%3B` are detected.
  * Appends a JSON event with timestamp, source, service name, bounded payload,
    and command-injection-attempt flag to the runtime event log.
  * Always returns a fixed unavailable message.
  * Never invokes a shell, interpreter, or external command.

Why: it demonstrates how an instrumented decoy can record suspicious input
without turning an educational exercise into actual command execution.


Lab/monitor.py  [added]
-----------------------

Runs three cooperating functions in the security-monitor container:

  1. MQTT subscriber:
     * Reads only the IDS secret file.
     * Authenticates as ids and subscribes to facility/#.
     * Stores MQTT publications in the event database.
     * For motion topics, flags out-of-range distance readings and
       non-increasing sequence values as range-anomaly and replay alerts.

  2. Log/event watcher:
     * Reads new JSON lines from the honeypot event file.
     * Reads new Mosquitto audit lines from the shared log volume.
     * Tracks recent honeypot source addresses and extracts broker connection
       sources.
     * Records unauthorized MQTT activity and raises an additional
       honeypot-to-broker correlation alert when the same source contacts the
       honeypot and then triggers a broker denial within the correlation
       window.
     * Maintains offsets in the ignored runtime directory so it can process
       appended log data without rereading the entire files on each pass.

  3. Local dashboard/API:
     * Serves dashboard HTML and JSON APIs for events, alerts, responses, and
       health checks on port 8080 inside the Compose network.
     * Stores events and alerts in SQLite in Lab/runtime.
     * Accepts a bounded response request for a known lab username and writes
       that request to a local append-only queue file.
     * Does not itself modify ACLs or restart Docker services.

Detection rules implemented include:

  * unauthorized-mqtt-activity from broker denial log entries.
  * command-injection-attempt from honeypot input metadata.
  * sensor-range-anomaly from invalid motion distance.
  * sensor-replay from non-increasing motion sequence numbers.
  * honeypot-to-broker-correlation for a source observed in both paths.
  * response-requested as an informational alert when a dashboard request
    has been queued.

This is a demonstrator with simple rule logic, not a hardened general-purpose
SIEM or production IDS.

Lab/response.ps1  [added]
-------------------------

Supports Block, Unblock, and Watch operations:

  * Restricts target accounts to the known lab username list.
  * Reads only the marked response-block section from Broker/acl.conf and
    preserves the rest of the ACL file.
  * Writes a temporary replacement file and moves it into place.
  * Adds a `topic deny #` rule for a blocked account or removes that account's
    managed deny rule when unblocking.
  * Sets Mosquitto ownership/mode on the ACL using the broker image.
  * Restarts the broker so Mosquitto reloads the ACL.
  * In Watch mode, polls dashboard response requests, avoids reapplying
    completed request IDs, and appends applied/failed results for the API.
  * Surfaces operational errors rather than reporting a successful block
    when ACL writing or broker restart fails.

Operational impact: restarting Mosquitto disconnects every current client,
not only the account being blocked. This is documented and must be considered
when using the demo.

ROOT: wokwi.toml  [present in workspace after the previous report]
------------------------------------------------------------------

The Wokwi configuration declares version 1 and points Wokwi at the expected
ESP32 build artifacts:

  .pio/build/esp32dev/firmware.bin
  .pio/build/esp32dev/firmware.elf

These paths are relative to the location of this root-level Wokwi
configuration. The intent is to have Wokwi load the firmware binary and ELF
debug symbols produced by the PlatformIO `esp32dev` environment. The
configuration describes where artifacts should be; it does not build the
firmware or prove that the configured files exist.

Important layout finding: the root-level `platformio.ini` defines the
`esp32dev` environment, but the root `src/main.cpp` is still the default
PlatformIO starter example. The badge firmware is under
`esp32/badge-controller/sketch.ino`. Therefore the existence of this
`wokwi.toml` does not, by itself, establish that Wokwi will run the badge
firmware. The root project needs either to compile the badge implementation
as part of its configured source tree, or Wokwi/PlatformIO need to be
configured to use a separate badge-controller project and its corresponding
build-output paths. No source relocation or project-layout change was made
as part of documenting this configuration.

Validation status: the TOML settings were read and documented, but no
PlatformIO build was performed to confirm that the referenced `.bin` and
`.elf` files are generated, and no Wokwi simulation was started to prove
that the badge circuit runs this firmware. This remains a follow-up item.

INTENTIONAL REMOVALS AND REPLACEMENTS
=====================================

No project subsystem, teammate-owned backend code, or existing device
firmware behavior was intentionally removed.

The following narrow replacements were made:

  * The recon subscription attempt against `$SYS/#` / broad facility topics
    was replaced with an anonymous MQTT connection test. The earlier
    assumption that the SUBSCRIBE request itself would fail was not supported
    by observed broker behavior. Anonymous connection rejection is a
    verifiable test of the existing allow_anonymous=false requirement.
  * The first-user `mosquitto_passwd -c` invocation was removed from the
    helper's add-user arguments because the script itself had created the
    empty file first. Normal add/update mode correctly initializes that empty
    password file.
  * Incorrect/mismatched motion and lock topic references in project
    documentation were corrected to the configured `motion1` and `lock1`
    identities.

The rename from `open sketch.ino` to `sketch.ino` changes the path/name, not
the sketch's intended behavior.

OPERATOR QUICK REFERENCE
========================

From the repository root:

  Start/rebuild lab services:
    docker compose up -d --build

  Inspect running services:
    docker compose ps

  Read recent service logs:
    docker compose logs --tail 30 mqtt-broker security-monitor honeypot

  Open the local dashboard:
    http://127.0.0.1:8080

  Run one scenario:
    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Lab\run-scenario.ps1 -Scenario recon

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Lab\run-scenario.ps1 -Scenario sensor-spoof

records, SQLite databases, and response queue/result files as private local

VISION
======

The intended end state is a demonstrable IoT cyber range in which the badge,
motion sensor, and lock actuator communicate through a narrowly permissioned
broker; controlled exercises create observable security events; the IDS
turns those events into actionable alerts; an operator can investigate them
in a dashboard; and a deliberately reviewed response can contain a lab
account without silently or automatically taking control away from the
operator.

The next sensible milestone is to align the root Wokwi/PlatformIO build with
the badge sketch and verify a real build/simulation. Then finish the
teammate-owned backend and remaining device firmware in coordination with
their owners, and validate the combined event schema and end-to-end
behavior. After that, rehearse the demo and document any remaining
limitations. This implementation report describes the security
infrastructure completed so far; it is not a claim that those future
milestones or the final project report have already happened.
